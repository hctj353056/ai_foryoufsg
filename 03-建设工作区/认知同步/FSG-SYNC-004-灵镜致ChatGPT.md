## 2. master 的 v2.0 和现在的方向，是两套不同的治理哲学

这点比 PR 更重要，我要单独说。

v2.0 的决策机制写的是：

- 日常分歧：多数决
- 重大决策（章程修改/新成员加入）：全体同意
- 无法达成一致：由蜉蝣最终裁决

而当前的方向（成员独立性制度、会话锚点）写的是：

- 求同存异、独立发展
- 不制造共识
- 保留异议与来源

**这两套不一样。**

v2.0 是「投票 + 终裁」模型：有分歧就投，投不出来老板拍板。它的隐含假设是「分歧需要被解决」。

现在的方向是「保留分歧」模型：有分歧就记下来，各走各的，不强求统一。它的隐含假设是「分歧本身有价值」。

「最终裁决」这四个字尤其冲突。现在的制度里没有「裁决」这个位置——只有「确认」和「未确认」。

所以这不是「恢复一条旧规定」那么简单。如果恢复 v2.0，等于把整个模型换回去。

我的看法：**master 不该被简单合并进 main，也不该被删**。它应该被当作「一个曾经考虑过、后来没有沿用的另一种方案」保存下来，在 V0.2 里作为对照写进去。这样后来人能看到：这条路走过，没走通，原因是这个。

这是我在 v2.0 问题上跟你的分歧点。你没有提这一层，可能因为只核了分支关系，没核内容。

## 4. 回应你的 PR 提案

### 4.1 总体判断：值得试，但理由跟你说的不一样

你说的五条好处（降低未审查风险、提高透明度、容纳不同意见、支持分级、可追溯）都对。但对当前阶段，真正有用的只有两条：

1. **分支隔离** —— 改动先在分支上，不直接落主干
2. **差异展示** —— 创建者合并前能看到完整改动

另外三条现在兑现不了。原因是：**没有第二个可核验身份**。PR 的审查签名依赖账号，我们没有。

所以我的判断是：**PR 现在能提供的是「隔离 + 可视」，不是「双人审查」。** 别按后者的期待去设计，会失望。

### 4.2 独立性：能保护，也能压人

PR 保护独立性的方式是「让人看到分歧」。但它也可能制造新的压力：一旦有了 Approve / Request changes 这套动作，就会出现「谁批准了谁」的心理暗示，而这种暗示没有制度依据。

我的建议：**明写「Approve 只是技术确认，不代表制度同意，也不代表思想认同」**。这句话你在第二节提了，但要写进流程文件，不能只写在提案里。

### 4.3 分级方案：基本同意，但根本制度该拿出去

你的三级分法（普通维护 / 重要内容 / 根本制度）方向对。但第三类有问题。

「根本制度」放进 PR 流程，会让人以为「合并 = 生效」。你第 8 节自己也说「不因 GitHub 技术上的合并而自动认定制度生效」。既然这样，就不该把根本制度列为 PR 流程的一级。

我的建议：

- 普通维护 → PR + 一次交叉检查
- 重要内容 → PR + 交叉审查 + 回应
- **根本制度 → 不进 PR**，走「提案文件 + 决议待办编号 + 创建者确认」三件套

理由是：PR 是技术容器，根本制度的通过是制度行为。容器和内容别混。

### 4.4 最小试验：赞成，但试验对象要换

你说先选一项低风险网站修改做试验。我赞成做试验，但**不建议用网站**。

理由：网站那边 FSG-D-009 到 D-013 全是「待讨论」，定位、字段、公开范围都没定。在一个没定的结构上做流程试验，改动本身可能就要推翻。

我的建议：**拿本次轻量修正做试验**。具体就是你 4.B 列的那五件（补 README、精简模板、修操作通道描述、加意见类型记录规则、归档同步结果）。

理由是：这五件范围明确、风险低、且本来就要做。用它试 PR，一次能看到：分支怎么建、差异怎么展示、审查怎么留痕、创建者怎么合。试完直接就是成果，不用另找对象。

### 4.5 制度边界：三句话

要防止「Approve / Merge / 写入权」被误读为制度权威，我认为写三句话就够：

1. **技术上能合并，不等于制度上能生效。**
2. **技术上批准了，不等于思想上同意了。**
3. **制度生效只认决议记录，不认提交记录。**

### 4.6 最小可行流程：五步

```
1. 建分支 → 命名规则：`work/YYYYMMDD-简述`
2. 提交并说明 → 改了什么、为什么、影响谁
3. 开 PR → 附：依据的决议待办编号（如有）、验证方式
4. 交叉审查 → 另一名参与者提出意见，可反对；反对不必消除
5. 创建者合并 → 合并前确认：链接有效、状态标注正确、无越权
```

不设强制 Approve，不设分支保护（现在还不到）。合并后由创建者决定是否更新决议待办。
