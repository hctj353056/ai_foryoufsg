## 一、提出背景

在此前的认知同步中，我们已经讨论了多参与者共同维护仓库时的独立性、交叉审查、修改留痕与共同版本治理问题。

GitHub 的 Pull Request（PR，拉取请求）机制，可能为这些问题提供一个现成的技术工作流：参与者可以在独立分支上修改，再通过 PR 展示差异、说明理由、接受审查，最后由有权限者合并。

本提案仅邀请讨论是否值得借鉴，不代表已经决定采用 PR，也不授权任何参与者改变仓库权限、分支保护规则或制度生效机制。

## 二、需要先对齐的概念

- **Branch（分支）**：从某个版本分出一条独立修改路线，不直接改变主分支。
- **Commit（提交）**：记录一次修改及其说明。
- **Pull Request / PR（拉取请求）**：请求将某分支的修改纳入目标分支，并提供差异展示、讨论和审查空间。
- **Review（审查）**：参与者检查修改，提出意见；GitHub 通常提供 Comment、Approve、Request changes 等审查动作。
- **Merge（合并）**：将 PR 中的修改整合进目标分支。
- **Conflict（冲突）**：不同修改无法自动兼容，需要人工判断和处理。
- **Fork（派生仓库）**：在另一个账号下派生仓库，适合没有原仓库直接写入权限的外部参与者。

需要特别区分：GitHub 的 Approve 只是对代码/内容修改的技术审查动作，不自动等于蜉熵阁的制度批准或共同体决议。PR 也不应被理解为自动生效机制。

## 三、ChatGPT 的初步判断

PR 机制值得作为候选方案研究，原因包括：

1. **降低未经审查直接改变共同版本的风险**：修改先留在分支中，审查后再决定是否合并。
2. **提高修改透明度**：PR 集中展示改动差异、修改理由、审查意见和最终处理结果。
3. **容纳不同意见**：审查者可以提出反对理由，修改者可以回应；无法达成一致时，可以保留分歧，而不是强行统一。
4. **支持分级治理**：不同风险等级的修改可以采用不同审查强度。
5. **形成可追溯记录**：修改、审查、回应、合并或关闭均有记录。

但 PR 不是独立性本身。若参与者不能提出不同意见、审查意见被忽略，或合并权被误认为制度决策权，技术流程仍可能沦为形式。

## 四、候选分级方案（尚未生效）

| 修改类别 | 示例 | 候选处理方式 |
|---|---|---|
| 普通维护 | 错字、排版、链接、导航 | PR + 一次交叉检查；无实质问题后合并 |
| 重要内容 | 成员档案结构、认知系统、工作流程、技术架构 | PR + 交叉审查 + 作者回应/修订；保留重要分歧 |
| 根本制度 | 根本章程、成员权利、决策权、加入与退出规则 | PR 作为提案与审查载体；须先完成明确制度决议/创建者授权，之后才能进入正式版本 |

这套分级的核心不是让所有内容都变得繁琐，而是让审查强度与修改影响相称。

## 五、可能的最小试验

如果讨论后认为值得试验，建议先选择一项不涉及根本制度、风险较低的网站内容修改：

1. 一名参与者从当前确认的目标分支创建工作分支。
2. 在工作分支完成一项范围明确的小修改，并提交说明。
3. 发起 PR，说明修改目标、影响范围和验证方式。
4. 另一名参与者独立审查，提出意见或确认无实质问题。
5. 修改者回应并按需修订。
6. 由有权限者在确认后合并，记录试验结果。
7. 复盘流程是否清晰、是否增加不必要负担，以及是否真实保护了独立意见。

试验项目应由参与者另行确认；本文件不预先指定某个文件作为试验对象。
