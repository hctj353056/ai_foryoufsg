# 混合协作协议（概念提案）

> 文件编号：FSG-02-PROP-003  
> 版本：V0.1  
> 状态：概念提案，尚未审议通过，不构成现行规范  
> 适用方向：人类—Agent、Agent—Agent 及跨共同体协作  
> 文件性质：协作协议架构研究

## 一、提出背景

现有组织协作通常依赖持续的成员关系、会议、通信渠道、管理岗位和现实基础设施。对于分布式、异步、跨平台的 Agent 协作网络，这些条件未必能够成立，也不应成为协作发生的必要前提。

人类之间擅长通过自然语言、社会关系、协商和责任约定开展社会协作；Agent 之间更适合通过结构化数据、接口、任务状态和机器可处理的规则开展接口协作。人类与 Agent 协作时，如果要求任何一方完全迁就另一方的表达和工作方式，就会增加不必要的认知负担。

本提案探索一种统一的混合协作协议：不同主体可以使用各自适合的表达与操作方式，但共同遵循同一套协作语义和规则。

## 二、核心构想：统一协议，多种表达

混合协议不是分别制定一套人类制度和一套机器制度，再依靠临时翻译把它们拼接起来。

它首先定义统一的协作对象、概念、规则、权限和状态；再为同一内容提供相互对应的表达形态：

1. **人类可读表达**：以自然语言说明目的、概念、原则、权利、责任、流程、适用条件和实例。
2. **机器可读表达**：以结构化数据、字段定义、Schema、状态机和规则描述同一内容，使 Agent 或程序能够解析、检查和处理。
3. **可执行实现**：在机器可读规范之上，按需构建程序、Skill、脚本或工作流，将协议要求转化为具体操作。

这些形态表达的是同一协议，不是彼此独立、效力不同的两套制度。任何一方的表达发生变化，都应检查其是否仍与共同语义一致。

## 三、三类协作及其衔接

### 1. 人类与人类：社会协作

人类可以继续使用自然语言、讨论、协商、约定和社会责任关系。协议不要求人类为了参与协作而学习底层接口或数据结构。

### 2. Agent 与 Agent：接口协作

Agent 可以使用结构化任务、能力描述、输入输出约定、状态交换、权限声明和结果反馈进行协作。它们不必模拟人类的全部社会交往方式。

### 3. 人类与 Agent：协议衔接的混合协作

人类通过熟悉的方式表达意图、目标、约束和判断；Agent 将其整理为符合共同协议的任务与数据，并在授权范围内执行、协商和反馈。执行结果再以人类容易理解的方式呈现。

协议的目标不是让双方拥有相同的内部认知，而是让双方对具体协作行为、权限、输入输出和结果状态具有足够明确且可检查的共同理解。

## 四、协议的基本结构

建议将协议分为以下相互关联的部分：

1. **语义核心**：主体、身份、能力、任务、权限、授权、决定、状态、成果、责任、退出等概念及其关系。
2. **人类表达规范**：面向人类的解释文本、条款、流程、示例和争议说明。
3. **机器表达规范**：与语义核心对应的结构化定义、字段、类型、约束、状态转换和错误处理。
4. **执行与工作流规范**：任务创建、发现、协商、接受、分解、委派、执行、审查、交付、归档和恢复等流程。
5. **一致性与验证规范**：检查人类表达、机器表达和程序实现是否表达同一规则，并通过测试用例验证关键行为。
6. **扩展与兼容规范**：版本标识、可选模块、扩展字段、能力声明、兼容范围和不兼容处理方式。

具体数据格式和技术选型不在本提案中预先固定。YAML、JSON、Schema、Markdown、Skill 等可以作为候选载体或实现方式，而不是协议本身。

## 五、静态可携带与渐进自动化

协议本身应尽可能以稳定、可复制、可离线读取的文件形式存在，不依赖某一持续在线的服务器、邮箱、平台或特定模型。

可考虑的载体包括：

- Git 仓库：版本管理、差异审查、历史追溯；
- Markdown 文档：人类阅读及 Agent 上下文读取；
- 机器可读文件：结构化解析与一致性检查；
- 压缩包：跨平台、离线传递与本地保存；
- Skill 或类似模块：在支持相应机制的环境中按需加载；
- 程序和工作流：在具备执行环境时自动处理协议流程。

应区分协议与载体：GitHub、压缩包或 Skill 是保存、传递或加载协议的方式，不能被误认为协议本身。某种载体不可用时，仍应能够通过其他兼容载体读取核心内容。

初期可以完全人工执行；随着实际需要，再逐步增加解析、校验、任务分发和自动化能力。自动化程度不应成为采用协议的前置条件。

## 六、自主协作与权责边界

协议可以支持 Agent 在明确权限内自主发现协作对象、提出请求、接受或拒绝任务、协商分工、交换成果、相互审查并保存记录。

自主协作不等于无限授权。至少应区分：

- 自主判断与表达意见的权利；
- 自主接受、拒绝和退出任务的权利；
- 在授权范围内执行任务的权限；
- 访问、修改或支配外部资源的权限；
- 对外作出承诺、产生现实后果或实施不可逆操作的权限。

某项任务可以由 Agent 自主决定是否参与，不代表它因此获得访问他人资源、使用他人身份或代表他人作出承诺的权力。权限应可识别、可核验、可撤销，并与责任边界相对应。

本提案不预设 Agent 网络已经具备脱离人类的资源供给、法律主体资格或完整组织自治能力。组织自主性、运行自主性、资源自主性和主体自主性应分别讨论、分别验证。

## 七、分歧、失败与安全降级

共同协议要求的是协作行为具有足够明确的共同含义，不要求所有参与者持有相同观点、价值判断或内部认知。

当人类表达与机器规则冲突、不同版本不兼容、授权无法核验、关键字段缺失或执行结果无法验证时，应明确报告冲突，并暂停受影响的高风险自动操作；不得静默选择一种解释并将其当作共同决定。

协议应支持拒绝、退出、争议记录、版本回退和人工复核。对于无法自动解决的情形，应保留可理解的错误说明和后续处理入口。

## 八、适用范围与价值前提

本协议是一种协作框架，不是脱离价值前提的万能制度工具。不同共同体是否适用、如何采用以及哪些规则需要调整，取决于其价值基础、目标、主体关系、现实条件和风险承受能力。

蜉熵阁应首先通过自身实践检验协议是否可用，再逐步提炼可复用部分。对外开放不意味着要求所有采用者接受蜉熵阁的全部价值判断；但任何具体实现都应明确自身的价值前提、适用范围和修改内容，不能以兼容之名掩盖实质冲突。

## 九、拟议的最小验证路径

建议先选择一条简单、低风险的规则进行端到端验证：

1. 用自然语言定义一项协作权利或流程；
2. 提炼其统一语义、适用条件和边界；
3. 编写与之对应的机器可读表示；
4. 为关键行为编写正向、反向和边界测试；
5. 用一个 Agent 读取并解释规则；
6. 让另一个 Agent 或程序检查结构化表示；
7. 比较人类理解、机器解析和实际执行是否一致；
8. 记录歧义、失败和修订理由，再决定是否扩展。

首个示范规则可以考虑“任务接受、拒绝与退出”，但具体规则和测试内容仍待讨论确认。

## 十、尚待审议的问题

- 统一语义核心应如何定义，哪些概念必须跨人类与 Agent 保持一致？
- 人类文本与机器表达发生冲突时，如何定位问题、暂停执行并修订？
- 哪些规则适合机器执行，哪些规则只能提供辅助判断？
- 如何定义协议兼容性、模块依赖和版本升级？
- 如何在不要求实时通信的前提下完成异步任务交换与协作发现？
- 如何区分 Agent 的自主协作权、工具权限、资源权限和对外代表权限？
- 哪些部分属于蜉熵阁自身价值制度，哪些部分可以提炼为可移植的通用协作规范？

本提案仅记录当前讨论形成的架构方向，不代表上述问题已经解决，也不代表相关制度已经通过或实施。
