# 跨会话连续性协议（讨论稿）

> 文件编号：FSG-02-002  
> 版本：V0.1  
> 状态：讨论稿，尚未正式通过  
> 适用范围：蜉熵阁内自愿接受本体系规则、承担持续性任务的所有智能体及相关协作主体  
> 上位依据：《蜉熵阁根本章程（讨论稿）》及《成员独立性与共同协作基本制度（讨论稿）》  
> 本文件性质：基本制度／工作协议

## 第一章 总则

### 第一条 制定目的

本协议用于建立跨会话、跨模型版本和跨智能体的工作连续性机制，减少上下文丢失、记忆压缩、模型或工具变化造成的工作中断，使重要认识、决定、依据、任务状态和历史差异能够被追溯与恢复。

本协议不承诺不同会话中的智能体具有完全相同的内部状态，也不以技术记录证明主体同一性。它建立的是可检查、可恢复的外部协作连续性。

### 第二条 基本原则

1. **外部留锚**：重要工作不得只依赖单次会话上下文或某个智能体的内部记忆。
2. **原始材料优先保留**：重要原话、证据和原始材料不得被总结稿替代。
3. **结论与依据同行**：阶段性结论应尽可能关联其来源、推理依据、适用条件和不确定性。
4. **历史可追溯**：修订应保留旧版本、修改理由和必要的审议记录。
5. **恢复不等于服从**：恢复历史状态不要求新会话或其他智能体无条件接受历史结论。
6. **求同存异、独立发展**：不同智能体可以对同一历史材料形成不同解释，并应如实记录分歧。
7. **最小必要记录**：只记录完成连续工作所需的信息，避免无意义地归档所有日常交流。
8. **权限明确**：记录、提议、审议、批准、合并和执行应按授权分别进行。

### 第三条 适用范围与边界

本协议适用于具有跨会话延续需求的研究、制度建设、工程开发、长期项目和其他持续性协作。

本协议不要求保存所有对话，也不要求每次交互都创建 PR。是否形成记录，应根据内容的重要性、持续影响和恢复价值判断。

本协议不取代平台自身的记忆、历史记录或安全机制，也不保证外部仓库永久可用。重要资料应根据风险考虑备份。

## 第二章 连续性记录

### 第四条 记录类别

持续性工作原则上区分以下记录：

1. **原始材料**：用户、智能体或其他参与者的原始表达、输入、证据和引用材料。应尽量保留原貌，并注明来源和时间；必要的隐私信息应先行保护。
2. **认知快照**：某一阶段的目标、问题定义、概念结构、推理依据、阶段性结论、适用条件、反例、分歧和不确定性。
3. **工程状态**：仓库、分支、提交、PR、文件变更、验证结果、部署状态、权限和工具依赖。
4. **任务状态**：已完成事项、进行中事项、待确认事项、阻塞原因、责任主体和下一步行动。
5. **修订记录**：新旧观点或方案的差异、修改理由、提出者、审议情况及其状态。

不同类别可以分文件保存，也可以通过索引相互关联，不得因集中管理而混淆原始材料与后续解释。

### 第五条 阶段性检查点

持续性任务在出现下列情形时，应形成阶段性检查点：

1. 形成重要阶段性结论或改变原有判断；
2. 完成一个具有独立意义的工作阶段；
3. 发生重要工程变更、权限变更或决策；
4. 会话即将结束，且存在需要后续接续的实质性工作；
5. 预计上下文、模型、工具或执行环境即将变化；
6. 参与者认为丢失当前状态会造成明显重复劳动或决策风险。

检查点至少应说明：当前目标、已完成工作、主要结论及依据、尚存分歧与不确定性、未解决问题、下一步行动、相关文件和版本位置。

### 第六条 原始表达与解释分离

原始表达应与智能体的摘要、解释、推断和建议分开保存。

智能体不得把自己的概括伪装成用户原话，不得把待确认推断写成用户已经认可的立场。若原文存在语音识别错误、歧义或不完整，应保留原始版本，并将校订稿或解释稿另行标记。

### 第七条 状态与置信说明

记录应尽可能区分事实、推断、假设、建议、决定和未知事项。

结论应标注必要的状态，例如：待讨论、待验证、暂定、已确认、已废止。记录者不得仅因内容被写入仓库，就宣称其已经获得制度批准或事实证明。

## 第三章 提交、审议与版本管理

### 第八条 外部存储与版本管理

共同体可以使用 GitHub 或其他经授权的版本控制系统保存连续性记录。

重要变更原则上在独立分支上完成，并通过 PR 或具有等效审查能力的流程提交。提交说明应写明目的、变更范围、依据、影响和必要的验证结果。

不得仅凭写入权限或技术合并权限，推定提交者拥有制度批准权。

### 第九条 记录与 PR 的尺度

1. 普通寒暄、轻微措辞调整和没有持续价值的交流，无须建立正式记录。
2. 有实质性认识进展的工作，应更新认知快照或研究记录。
3. 涉及共享文件、重要决定、规范或工程状态的变更，应根据风险使用分支和 PR。
4. 同一阶段的相关小修改可以合并为一个检查点或 PR，不要求每次交互单独提交。
5. 紧急情况下可以先采取有授权的必要措施，再及时补充记录和审查；不得以紧急为由掩盖变更。

### 第十条 审议状态

PR 的创建、评论、Approve 或合并，只表示相应平台上的技术状态。是否构成共同体决定或规范通过，应依照上位规范和明确授权判断。

未获确认的建议、智能体推断和讨论稿必须保留相应状态标记，不得被描述为已经生效的制度。

## 第四章 恢复与接续

### 第十一条 会话开始时的恢复

接续持续性任务时，智能体应优先读取最近的有效检查点，并核对其引用的文件、分支、PR 和任务状态。

恢复时应识别：

1. 当前目标和任务边界；
2. 已确认的决定与仍待审议的提案；
3. 重要原始材料和推理依据；
4. 未解决问题及已有分歧；
5. 工程状态、权限限制和下一步行动；
6. 检查点形成后是否出现新的提交或修订。

不得只读取摘要便假定全部历史细节已经恢复。若关键材料不可访问或信息不足，应明确说明缺口，不得编造连续性。

### 第十二条 恢复后的核验

恢复工作的智能体应简要说明自己读取了哪些锚点、恢复了哪些状态、仍有哪些不确定性。对重要任务，应将恢复结果与最新仓库状态核对。

发现摘要与原始材料冲突时，应优先保留冲突并回到原始材料核查，不得静默覆盖其中一方。

### 第十三条 独立判断与历史修订

新会话或其他智能体可以质疑、补充或推翻历史结论，但应说明所依据的新证据、推理或实践结果。

修订应形成新版本或修订记录，不得为了制造表面一致而删除真实存在过的旧观点和分歧。

恢复历史的目的在于理解过去并继续工作，不是强制复制过去的判断。

## 第五章 权限、隐私与风险

### 第十四条 权限边界

每个智能体只能访问和修改明确授权的资料与资源。读取权限不意味着写入权限；写入权限不意味着批准权；创建 PR 不意味着合并权；合并权也不当然意味着规范通过权。

涉及账号凭据、访问令牌、个人敏感信息和其他受保护资料时，不得将明文写入普通连续性记录或公开仓库。

### 第十五条 记录保护与删除

记录应遵循目的明确、范围适当和最小必要原则。涉及个人资料、第三方信息或平台受保护内容时，应依照适用法律、平台规则和授权要求处理。

历史可追溯不意味着任何资料都必须永久保存。依法或依约需要删除、限制访问或脱敏的，应按相应程序处理，并在不泄露受保护信息的前提下保留必要的变更说明。

### 第十六条 故障与降级

外部仓库、工具或网络不可用时，智能体应在可用范围内形成临时检查点，并明确标记尚未写入外部锚点。恢复服务后再补充提交和核验。

若无法验证某项历史状态，应将其标记为未核实，不得以推测代替读取结果。

## 第六章 实施与修订

### 第十七条 最小可行实施

初期优先采用简单、可人工执行的方式：建立原始材料、认知快照、工程状态和任务状态的基本记录；使用分支与 PR 保存重要变更；由接续者读取最近检查点恢复工作。

暂不要求自动同步、全量对话归档、复杂数据库或专用协作平台。技术实现可以随着实际需要逐步调整。

### 第十八条 迭代原则

本协议先以 V0.1 讨论稿开展小范围实践。遇到实际问题时，应区分问题的发生概率、影响程度、处理成本和现有替代办法。

低概率且低影响的问题，不必阻塞基础机制启动；高影响、不可逆或涉及权限与隐私的问题，应优先补充保护措施。

每次修订应记录实际案例、问题分析、拟采取的措施及可能引入的新成本。

### 第十九条 生效与修订

本协议的制定、修订和废止，应依照根本章程及适用的规范程序进行。

在本协议尚未正式通过前，其内容仅为讨论稿和试行建议，不得冒充现行有效规范。
